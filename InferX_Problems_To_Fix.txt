--- Batching (app/batching/queue.py, scheduler.py) ---

P2-1  Multi-row requests corrupt results / leak data            [RAN]  Effort M
WHERE   queue.py lines 68-71: `future.set_result(results[i:i+1])`
WHAT    The splitter assumes every request has exactly one row. Verified: request
        1 with 2 rows got back 1 row, and request 2 (value 5) received 2.0 (the
        first request's leftover), i.e., one caller sees another caller's data.
FIX     Record each request's row count when enqueued (`n = x.shape[0]`), then
        slice by cumulative offsets:
            offset = 0
            for (req, fut), n in zip(items, sizes):
                fut.set_result(results[offset:offset+n]); offset += n
        Also enforce `max_batch_size` in ROWS, not requests.
VERIFY  Unit test: mix of 1-, 2- and 3-row requests; assert each caller gets its
        own outputs, in order (compare against calling the backend individually).

P2-2  First-request wait is measured from dequeue, not enqueue  [READ] Effort S
WHERE   queue.py lines 35-40
WHAT    `deadline = time.time() + max_wait` starts after the first item is taken,
        so time the request already spent queued (behind an in-flight batch)
        is not counted; actual wait can exceed max_wait.
FIX     Stamp `enqueue_time` in `enqueue()` and compute the deadline from the
        oldest request's enqueue time.

P2-3  Lone request always waits the full max_wait               [RAN]  Effort S
WHERE   queue.py lines 41-50
WHAT    Verified: a single request took ~51 ms with max_wait=50 ms. At the
        configured 5 ms, every low-traffic request pays +5 ms for nothing, which
        matters for 10-20 ms budgets.
FIX     If the queue is empty and no batch is executing, dispatch immediately
        ("work-conserving" batching), or only wait when concurrency > 1. Make
        `max_wait` adaptive to the request's remaining latency budget.

P2-4  Malformed input poisons the whole batch                   [READ] Effort S
WHERE   queue.py lines 58-63
WHAT    One request with a different shape/dtype makes torch.cat/np.concatenate
        raise; every request in that batch receives the exception.
FIX     Validate shape/dtype at the API boundary (and in enqueue) against the
        model's expected input; on batch failure, retry items individually to
        isolate the culprit.

P2-5  Pending futures hang on shutdown/cancel                   [READ] Effort S
WHERE   queue.py lines 20-27 and 77-78
WHAT    stop() cancels the worker; items still in the queue (and the in-flight
        batch) keep unresolved Futures, so awaiting callers hang forever.
FIX     On stop: drain the queue and `set_exception(RuntimeError("shutting
        down"))` on every pending future; handle CancelledError during the
        executor await by failing that batch's futures.

P2-6  Unbounded queue, no back-pressure                         [READ] Effort S
WHERE   queue.py line 13 (`asyncio.Queue()`)
WHAT    Under overload the queue grows without bound; latency explodes and memory
        grows. No per-request timeout either.
FIX     `asyncio.Queue(maxsize=N)`; on full -> immediately return 503/429
        ("load shedding"). Add a per-request deadline: drop requests that
        already exceeded their budget before execution.

P2-7  Small code-level issues in the batcher                    [READ] Effort S
WHERE   queue.py lines 40, 55-56, 65; scheduler.py lines 30, 34
WHAT    - `time.time()` should be `time.monotonic()` (wall clock can jump).
        - `import torch`/`numpy` inside the hot loop on every batch; move to
          module level.
        - `asyncio.get_event_loop()` is deprecated in coroutines; use
          `get_running_loop()`.
        - Scheduler bypass path (batching disabled) and the queue path both call
          backend.predict directly, SKIPPING ModelManager.predict's health check.
        - Only one batch in flight per model; no pipelining.
        - Hard dependency on torch even for ONNX-only deployments (the import is
          unguarded).

P2-8  Over-budget models are not excluded                       [RAN]  Effort S

FIX     Hard-filter candidates whose p95 exceeds the budget (keep a "best effort"

P2-9  Scoring ignores most of its configuration                 [READ] Effort M
WHERE   scoring.py; router.py lines 9-12; config.yaml routing section
WHAT    - `accuracy_priority` ("balanced"/"high"/...) is in the API example but
          never read.
        - `health_weight` and `load_weight` are configured but unused, so
          "routes by health and load" is untrue.
        - Weights are not normalised; hardcoded fallbacks (0.4/0.6) differ from
          the YAML (0.4/0.3).
        - p95_latency_ms/accuracy must pre-exist in metadata; defaults (50 ms,
          0.5) silently apply when missing, so un-benchmarked models look
          average.
FIX     Map accuracy_priority -> weight multipliers; add health (breaker/error
        rate) and load (queue depth / in-flight) terms; normalise weights to sum

        without benchmark metadata.

P2-10 Registry connection handling                              [READ] Effort M
WHERE   app/models/registry.py (all methods)
WHAT    - New psycopg2 connection per call (adds ms per request; no pooling).
        - `with psycopg2.connect(...) as conn:` commits/rolls back but does NOT
          close the connection => connection leak under load.
        - Errors are logged and swallowed: get_active_models returns [] on a DB
          outage, so a database failure looks like "no models", producing
          misleading errors.
        - `_init_db()` runs in __init__ and swallows failures: in docker-compose
          Postgres may not be ready yet, so the table is never created and later
          queries fail forever.
        - Synchronous driver called from async code blocks the event loop.
        - `precision`, `metadata` etc. fine, but no indexes on (model_name,
          status).
FIX     Use a connection pool (psycopg_pool / asyncpg / SQLAlchemy async). Retry
        init with backoff on startup (or use migrations: Alembic). Let errors
        propagate (or return a typed error) and surface them as 503. Cache
        ACTIVE rows in memory with a short TTL or refresh on status change
        (LISTEN/NOTIFY) so routing does not hit the DB per request.

P2-11 Canary/rollback statistics and edge cases                 [READ] Effort M
WHERE   canary.py lines 26-32; rollback.py lines 19-27
WHAT    - Rollback fires on one P95/error sample with no minimum sample size or
          time window: a few slow requests can fail a good canary; with 5%
          traffic you may take minutes to collect meaningful data.
        - Canary comparisons ignore load differences (canary sees different
          traffic mix/time).
        - Error-rate check is independent of stable's error rate (a global 2%
          threshold even if stable is at 3%).
        - Per-request random assignment is not sticky (a user can bounce between
          versions); a canary that is picked for batching joins a different
          queue so batch sizes shrink.
        - No auto-promotion; rollback only logs and flips status (no event/metric).
FIX     Require min_samples and min_duration; compare with a confidence
        interval (bootstrap P95, or a two-proportion test for errors); use
        hash(user_or_session_id) % 100 < pct for stickiness; emit metrics/events;
        add `promote()`.

--- Resilience ---

P2-12 Retry and fallback semantics                              [READ] Effort S
WHERE   app/resilience/retry.py, fallback.py
WHAT    - Retries ALL exceptions, including permanent ones (bad input, shape
          mismatch) which can never succeed.
        - Backoff sums to 0.7 s+ (0.1+0.2+0.4) which exceeds typical 20-100 ms
          budgets; no deadline awareness.
        - Jitter is only +0..10% of the delay; "full jitter" (Uniform(0, delay))
          de-synchronises clients far better.
        - No retry budget => retry storms during an outage.
        - Fallback catches every exception, logs only the string, emits no
          metric, and can mask bugs.
FIX     Retry only an allow-list (TimeoutError, transient runtime errors); pass
        the remaining budget and stop when exhausted; use full jitter; cap retry
        ratio; count fallbacks in a metric and annotate the response
        (`fallback_used: true`).

P2-13 Circuit breaker details                                   [RAN]  Effort S
WHERE   app/resilience/circuit_breaker.py
WHAT    - HALF_OPEN lets EVERY request through (verified two consecutive
          can_execute() calls both True) although the comment says "allow one
          request"; a recovering backend gets flooded.
        - `time.time()` instead of `time.monotonic()`.
        - Not thread-safe; failure counter has no time window (consecutive
          failures hours apart still trip it).
        - Counts any exception equally (client errors vs server errors).
FIX     Track `half_open_in_flight` and allow a small number of probes
        (e.g., 1-3), require N successes to close, use monotonic time, add a lock
        if used across threads, and only count backend/server failures.
VERIFY  Test the full state machine with a fake clock.

--- Inference / optimisation pipeline ---

P2-14 ONNX input dtype and GPU tensor handling                  [READ] Effort S
WHERE   app/inference/onnx_backend.py lines 36-41
WHAT    A float64 ndarray (NumPy's default) is passed straight to ORT, which
        raises "Unexpected input data type" (model expects float32). A CUDA torch
        tensor makes `.numpy()` fail (needs `.cpu()`).
FIX     `x = np.ascontiguousarray(x, dtype=np.float32)`; for tensors
        `.detach().cpu().numpy()`. Validate shape against
        `session.get_inputs()[0].shape`. For CUDA use IO binding to avoid copies.

P2-15 PyTorch backend limitations                               [READ] Effort S
WHERE   app/inference/pytorch_backend.py
WHAT    - Models hard-coded in an if/elif chain (only mobilenet_v3_small,
          resnet18).
        - `pretrained=True` is deprecated (use `weights=...`) and can be removed
          in future torchvision releases.
        - No torch thread control: with the default executor, several concurrent
          forward passes oversubscribe CPU cores (`torch.set_num_threads`).
        - Does not use `torch.inference_mode()` (slightly faster than no_grad).
